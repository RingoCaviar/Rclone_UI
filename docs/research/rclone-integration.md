# rclone integration and capability-discovery boundary

Research date: 2026-08-11  
Scope: supported, first-party rclone interfaces suitable for a Windows desktop GUI.

## Decision

Use a GUI-owned, long-lived `rclone rcd` child process as the primary integration boundary. Bind it only to loopback on an ephemeral or GUI-selected port, generate per-run credentials, pass the portable config/cache paths explicitly, and terminate it with `core/quit` (then process-tree termination as a crash fallback). Send typed JSON to its HTTP RC endpoints and discover the installed binary's contract at runtime. Do not parse human-oriented CLI output for normal operation and do not compile a static mirror of providers, flags, or backend features.

Keep direct CLI execution as a narrow compatibility/diagnostic escape hatch: version/bootstrap checks, commands for which the running version exposes no RC endpoint, and raw “advanced command” mode. In that path prefer documented JSON output (`lsjson`, `about --json`, configuration JSON commands) and treat stderr/stdout text as logs, not an application protocol.

The RC server must never be exposed to the LAN. rclone states that RC access is equivalent to shell access: it can execute commands, read/write local files, expose stored credentials, mutate configuration, and stop rclone; it has no per-endpoint scopes. The official default is loopback, but the GUI should additionally require authentication and never use `--rc-no-auth` ([RC security](https://rclone.org/rc/#security)).

| Remote enumeration and storage paths | `config/listremotes`, `config/get`, `config/paths`; `core/disks` for GUI local roots | `config/listremotes` includes config-file and environment-defined remotes. | Provider and option discovery | `config/providers`; `options/info`, `options/get`, `options/blocks` | Provider and global-option descriptions are `Option` records containing name/type/default/help/examples, password/sensitive/advanced/required/exclusive/visibility metadata. rclone explicitly documents these as suitable for building UIs ([Option blocks](https://rclone.org/rc/#option-blocks), [config providers](https://rclone.org/commands/rclone_config_providers/)). |
| Create/update remote | `config/create`, `config/update`, `config/password`, `config/unset`, `config/delete`; OAuth status/stop where present | Run create/update in `nonInteractive` mode. Do not use recursive listing for an interactive folder page by default. |
| Directory transfers | `sync/copy`, `sync/move`, `sync/sync` with per-call `_config` and `_filter`; single-file operations via `operations/copyfile`/`movefile` | Run long operations with `_async: true`; rclone specifically recommends async execution for these operations. Dry-run belongs in per-call config and must remain a first-class GUI preview mode. |
| Progress/history | Set a unique `_group`; poll `job/status` and `core/stats group=...`; read `core/transferred group=...` | Stats expose aggregate bytes, totals, ETA, speed, errors, checks, deletes, active transfers and per-file progress. | Cancellation | `job/stop jobid=...`; optionally `job/stopgroup`; `core/quit` only for shutting down the owned daemon | Cancellation is cooperative through the job context. | Mount lifecycle | `mount/types`, `mount/mount`, `mount/listmounts`, `mount/unmount`, `mount/unmountall`; `options/info/get` blocks `mount` and `vfs` | Discover available implementations with `mount/types`; pass typed `mountOpt` and `vfsOpt`. On Windows, `mountPoint: "*"` requests the next drive letter and the response contains the actual mount point ([mount RC endpoints](https://rclone.org/rc/#mountmount-create-a-new-mount-point)). Windows CLI mounts are foreground-only, reinforcing ownership by the long-lived daemon ([mount documentation](https://rclone.org/commands/rclone_mount/)). Endpoint absence or no returned mount type disables mount UI even if WinFsp is installed. WinFsp installation detection is an application/platform concern, not an rclone capability endpoint. |

Use it to enable operations for each remote instance, including wrapper remotes; never infer solely from provider type ([operations/fsinfo](https://rclone.org/rc/#operationsfsinfo-return-information-about-the-remote)). Backend-specific commands go through `backend/command` but their command/option schema is backend-defined, so expose them as advanced features rather than generic core UI ([backend/command](https://rclone.org/rc/#backendcommand-runs-a-backend-command)). |

## Capability model and fallbacks

Build a capability snapshot at daemon startup and refresh it after rclone replacement or config changes:

1. Record `core/version` and the `rc/list` endpoint set.
2. Load provider/global schemas from `config/providers` and `options/info`; cache them only for that exact bundled binary version.
3. Load `mount/types` when present.
4. For each configured remote/root, call `operations/fsinfo`; cache by canonical remote configuration and invalidate after edits.
5. Treat endpoint/schema/feature absence as unsupported and hide or disable the action with an explanation. Unknown JSON fields must be retained or ignored safely, never rejected.

There is no single discovery call that proves every command will succeed. `fsinfo.Features` describes optimized/optional backend primitives, while many high-level operations can still work through rclone fallbacks. Therefore capabilities should have three states: **available** (endpoint and required primitive/data exist), **unavailable** (endpoint missing or an explicit false blocks it), and **attemptable** (high-level rclone operation exists but performance/semantics depend on fallback). Let rclone return the authoritative operational error.

Provider metadata is sufficient for a complete generic configuration UI, but not necessarily a polished provider-specific experience. The GUI may layer curated forms for common providers, provided the submitted keys still come from the live schema and the non-interactive state machine remains the final authority.

## Contract and safety requirements

- Launch only the bundled, verified `rclone.exe`; do not search `PATH` implicitly. Record its version with task diagnostics.
- Use JSON POSTs and structured RC errors. Assign an application correlation ID via `_group`; redact passwords, tokens, config dumps, RC credentials, and sensitive option values from logs.
- Never use `core/command` for ordinary features. It runs arbitrary rclone commands and expands the already shell-equivalent RC attack surface ([RC security](https://rclone.org/rc/#security)).
- Avoid `config/dump` in routine UI flows because RC can return stored credentials. Use `config/listremotes` and targeted `config/get`, and redact sensitive values before persistence or diagnostics.
- Do not assume RC jobs survive GUI/rclone process restart. Persist task definitions and terminal history in the app; on startup, reconcile current `job/list` and mounts from the newly owned daemon, marking interrupted prior jobs accordingly.
- Validate behavior against the minimum supported bundled rclone and latest candidate during updates. Runtime discovery permits graceful evolution but does not replace compatibility tests for JSON field/type changes.

## Answer to issue #3

The reliable boundary is a locally owned `rclone rcd` process and its documented JSON RC endpoints. It covers remote configuration (including rclone's non-interactive question state machine), schema discovery, browsing and mutations, asynchronous copy/move/sync, progress, cancellation, mounts, and per-remote capabilities. `rc/list`, `config/providers`, `options/info`, `mount/types`, and `operations/fsinfo` together prevent a fragile hard-coded mirror. Direct CLI JSON commands remain a deliberately small fallback; human-readable CLI output is never a data contract.
